# 研究点一：先进方案对比与补实验核查

日期：2026-10-17。范围：本地研究点一正文、基准脚本、已保存结果与代表性论文。此次为核查和实验建议，未修改现有实验实现、论文或PPT，未运行新的性能对比。

## 判断

建议补强完整协议的性能对比。现有收敛、反演和聚合正确性实验支持功能与训练效果；现有跨方案数据仅覆盖掩码层，不能据此证明完整可验证安全聚合协议优于先进方案。研究优势应具体落在客户端计算、交互、通信、掉线恢复及系统成本分布上，不应将精度接近FedAvg称为SOTA。

## 已核实的现状与问题

1. 毕业论文第3章已有VeriFL、VLMRS、GPVO-FL的掩码层对比，并明确写出非官方实现和不含完整验证。来源：`E:/bjtu-thesis/chapters/chapter03.tex` 第945行起。会议稿的开销比较主要列VeriFL和VLMRS，来源：`E:/bs2026/main.tex` 第400行附近。
2. `E:/hvsa/exp_overhead_crypto.py` 第108行明确：`masking + cloud-side ingress only; excludes LHH/signatures/pairing`。因此，当前图不能回答完整协议的验证成本比较。
3. `E:/hvsa/baselines/crypto_common.py` 第28—50行使用10 Mbps、每邻居20 ms RTT的顺序交互模型；`secagg_crypto.py` 第78行、`gpvo_crypto.py` 第85行将`crypto_ms + p2p_tx_ms`填入`comp_user_ms`。这是实测密码计算与建模网络等待的混合指标，不应标为纯计算耗时，也不代表实测网络端到端耗时。
4. `hvsa_crypto.py` 第60行在轮次计时外建立TA共享种子。需要分别报告初始化、稳定轮次及多轮摊销，按各协议真实复用语义处理，不能任意要求其他协议每轮重复初始化。
5. 通信载荷口径不统一：`crypto_common.py` 第122行的通用上传默认每维4字节，HVSA调用该默认；`gpvo_crypto.py` 第64、68行按每维8字节统计。当前双方云侧都是M个向量；结果中0.191 MB与0.381 MB的约2倍差距不能按现有程序归因为“GPVO多一份掩码/验证向量”。需要统一合法编码、量化精度和真实消息序列后重计字节。
6. 第3章同段同时出现“HVSA唯一在N维度上用户计算和云侧入流双O(1)”和“GPVO-FL同为O(1)”，表述自相矛盾。对于固定M，应将差异落实为真实常数项、消息数及恢复机制，不能占用GPVO也具备的阶数性质。
7. 只报告云端O(Md)会忽略边缘和TA所承担的工作。新实验应同时列客户端、边缘、TA、云端，以及关键路径总时延，避免将转移工作量误称为系统总开销消失。

## 最小补实验建议

第一阶段先比较HVSA与GPVO-FL的完整协议，先确认工作点逐维聚合一致与验证接受/拒绝行为，再进行计时。可以回放同一批真实训练参数来测协议成本，无需为每种密码协议重新训练所有准确率曲线。

| 实验 | 建议设置 | 必须报告 |
|---|---|---|
| 完整协议成本 | 固定M=5；先做N=20、d=7,850的真链路，再扩展N=50/100与d=10k/100k | 分角色密码计算、初始化与稳定轮次、真实消息字节、协议轮次、关键路径时延。 |
| 验证成本 | LHH、签名、证明/承诺生成与验证均按原协议执行 | 客户端验证成本与外包后的边缘成本；实际计时与外推分开，不能用verify=False事务耗时替代验证耗时。 |
| 掉线与恢复 | 0%、10%、20%、30%，冻结同一参与集合与掉线轨迹 | 在各协议支持的阶段与阈值内比较成功率、恢复时延、额外通信、正确性；超阈值失败应如实列出。 |
| 安全与功能表 | 不以耗时替代安全比较 | TA是否可信且不合谋、边缘是否诚实、验证者位置、全局模型可见性、客户端交互、支持的掉线阶段。 |

每个计时工作点建议预热后至少10次，报告中位数和离散程度。不同实现语言或密码库造成的性能差异也需披露；对比相同安全等级、相同合法数值编码、相同N/M/d和网络配置。

第二阶段再增加LightVeriFL或补齐VLMRS的一条完整先进基线。SAEV-FL先完成机制和信任模型核对；不能仅因年份较新就直接拼接不兼容的耗时。

## 可使用的结论范围

实验前：在可信TA与诚实边缘假设下，方案旨在减少客户端交互和验证负担，并保持聚合正确性及训练效果。

实验后：仅按实际结果说明在具体配置下、相对具体基线降低了哪一类成本，并同时交代边缘及TA开销；若只减少客户端成本而系统总成本未降低，应直接说明成本分布变化，不写全面优于SOTA。
