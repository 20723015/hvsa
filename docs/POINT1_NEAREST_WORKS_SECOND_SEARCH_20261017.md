## 1. 新发现与判断

这轮最值得补充的并不全是2026年论文：

- OVP-FL（2025）直接研究验证外包和客户端减负。
- 同态MAC云边AIoT方案（2025）明确由边缘验证聚合结果，客户端另有进一步验证。
- OPSA（2025）已研究TEE辅助的一次上传/单掩码与结果验证。
- TriVer（2026-08-25）提供单掩码与客户端多项验证，但依赖BFT聚合节点集群、阈值签名和客户端间承诺广播。
- LPV-FL的作者接受稿将成对抵消掩码合称为单掩码，不能只凭名称认为它与HVSA每客户端一条TA掩码的操作量相同。

这些工作说明，“单掩码”“一次上传”“验证外包”“边缘验证”“验证通信不随模型维度增长”各自都有相关先例。是否在特定条件和指标上达到先进水平，仍须由同口径的完整协议实验决定；本轮不能据此认定HVSA全面领先，也没有完成证明某个组合绝无新颖性的穷尽调查。

## 3. 三个最有用的区别

### 3.1 OVP-FL与HVSA：验证外包已存在，具体服务结构不同

原文PDF第5页说明，OVP-FL将任务外包给两个验证服务器；TA在初始化之后一般离线；用户产生两份盲化梯度及辅助认证信息。原文允许聚合服务器与其中一个验证服务器合谋的场景。

当前HVSA的结构是：客户端与一个在线可信TA共享种子，上传一份掩码向量，边缘对组证据签名并核验聚合关系。比较可以落在上传份数、客户端操作、验证服务器/边缘成本和TA在线成本上，不能将“提出验证外包”本身视作HVSA首次提出。

这是功能与工作分配比较；本轮没有证明某一方案在所有合谋情形下都强于另一方案。

### 3.2 同态MAC云边方案：边缘验证减负已有直接先例

出版商摘要明确提到由边缘节点验证以减少客户端计算，并保留用户进一步检查。它采用同态MAC，HVSA采用LHH关系和签名组证据。

应比较证据生成者、验证者、验证密钥、用户是否还需验证，以及验证覆盖对象。其隐私保护与HVSA是否完全对齐，需取得全文后核对；不能仅因标题含secure aggregation就直接作为等价隐私基线。

### 3.3 OPSA与TriVer：可信设施和客户端通信不能省略

OPSA使用可信TEE；在没有SGX硬件与远程证明实现时，只能分别报告其原语成本或引用作者结果，不能把普通Python模拟称为真实TEE系统时延。

TriVer采用聚合节点BFT与阈值签名，并要求客户端间传播承诺。它提供了2026年的新近比较对象，但与单可信TA模型不同。本文对其安全性优越、攻击其他方案和原论文耗时的说法没有进行独立验证，不直接沿用为HVSA实验结论。

## 4. “单掩码”术语必须拆开

至少区分以下三类：

1. 一个客户端最终上传一个掩码向量，但该向量由多个成对PRG掩码相加得到，如本轮核对的LPV-FL。
2. 客户端与可信辅助方协商独立种子，每轮生成一条掩码，如当前HVSA。
3. 使用密钥同态PRF和聚合密钥恢复总掩码，如OPSA中的一条实例化路径及TriVer所述框架。

不能仅比较“单/双”字样。后续操作表应记录每客户端的DH/PRG次数、证明生成、持有密钥数、消息数，以及恢复所依赖的可信方/阈值。

## 6. 更新后的引用与实验优先级

### 引用和机制表

优先补齐或讨论：

1. GPVO-FL：最接近的分组与验证外包协议。
2. SAEV-FL：同团队、单掩码、云边协同、客户端解密验证及全局参数保密。
3. OVP-FL：双验证服务器的外包路径。
4. 同态MAC云边AIoT方案：边缘验证与用户进一步验证。
5. VLMRS：多轮复用与客户端验证。
6. OPSA、TriVer：可信TEE辅助与BFT聚合节点辅助的不同路径。

不要求每篇新增文献都做完整性能复现。EPVFL、EvaFL先取得原文，LPV-FL按正文讨论范围纳入。

### 性能实验

维持现有可执行主线：

- 第一阶段HVSA/GPVO完整协议。
- 第二阶段VLMRS完整协议。
- 如再加一个同架构/轻量掩码候选，优先评估SAEV-FL。
- 若重点要证明客户端因验证外包而减负，优先评估OVP-FL的完整实现；如仅比较验证原语，可评估同态MAC组件。
- TriVer与OPSA先做机制和假设对照；前者需要完整BFT/阈值/广播计量，后者需要真实TEE条件，暂不塞进首轮运行预算。

如后续对原文核对发现已有方案在相同模型下满足相同功能且成本更低，应记录结果并调整贡献定位，而不是排除该基线。

这些是补证据与界定贡献的建议，不是对录用论文作学术不端判断，也不是撤稿风险评估。
