# 研究点2草稿：基于双辅助服务器可验证安全聚合的分层半异步联邦学习

## 推荐题目

- 推荐题目：面向双辅助服务器可验证安全聚合的分层半异步联邦学习机制
- 备选题目：兼顾隐私保护与时延降低的分层半异步联邦学习方法
- 备选题目：基于窗口化安全聚合的分层异步联邦学习方法

说明：

- 这里的“双辅助服务器”在当前实现中对应 `TA1` 和 `TA2`。
- 为了和现有代码保持一致，下文仍可写作 `TA1`、`TA2`，但论文表述建议强调它们是辅助安全聚合的两个非串通逻辑服务器，而不是一个万能的全可信第三方。

## 1. 研究背景

研究点1已经解决了分层联邦学习中的隐私保护与结果可验证问题：用户仅上传一次掩码后的模型参数，边缘侧负责聚合与验证，云端在两个辅助服务器共同提供部分掩码后完成解掩码与全局聚合。该设计降低了单点信任并保持了用户侧 `O(d)` 级开销。

但是，现有研究点1本质上仍是按全局轮次驱动的同步聚合模式。边缘服务器需要等待其关联用户完成本地训练并上传，云端还需要等待所有边缘结果到齐后再执行全局更新。这种严格同步机制在设备异构、链路波动和用户掉线环境下会放大拖尾效应，导致高性能节点空闲等待，训练时延明显增加。

直观上，异步聚合可以缓解上述问题；但对当前安全聚合框架而言，不能直接照搬普通异步 FL。原因在于本方案的掩码生成、部分解掩码和边缘验证，都依赖于一个已经固定的参与集合。如果允许客户端级别的全异步提交，那么参与集合会持续变化，两个辅助服务器难以基于同一用户集合生成一致的部分掩码，边缘侧的哈希一致性验证也会失效。因此，研究点2的关键不是“把同步改成全异步”，而是设计一种与密码流程兼容的半异步机制。

## 2. 问题定义

### 2.1 核心问题

在研究点1构建的双辅助服务器可验证安全聚合框架基础上，如何在不破坏现有隐私保护、可验证性和掉线容忍机制的前提下，引入分层半异步聚合，以降低同步等待开销并提升系统收敛效率？

更具体地说，需要解决下面四个耦合问题：

1. 如何把“整轮同步聚合”改造成“窗口化聚合”，使每个边缘批次都拥有可封闭、可验证、可解掩码的固定参与集合。
2. 如何让不同边缘批次在云端异步提交与异步融合，同时抑制陈旧模型对全局模型造成的不稳定影响。
3. 如何保证异步机制不破坏双辅助服务器的部分掩码生成逻辑，即两个辅助服务器始终基于同一窗口标识和同一用户集合工作。
4. 如何在异步条件下仍保持边缘侧验证关系成立，使云端不能伪造、篡改或选择性丢弃聚合结果。

### 2.2 形式化问题表述

给定一个分层联邦学习系统，其中包含用户集合 `U`、边缘服务器集合 `E`、云聚合服务器 `C` 以及两个非串通辅助服务器 `A1` 和 `A2`，设计一种窗口化半异步安全聚合机制，使得系统在满足以下约束条件时，尽可能缩短达到目标精度所需的训练时间：

约束条件如下：

1. 每个用户仍只上传一个掩码后的模型参数向量，不增加用户侧协议分支。
2. 两个辅助服务器必须基于同一窗口的固定在线用户集合生成部分掩码。
3. 云端只有在收到该窗口对应的两份部分掩码后，才能恢复明文聚合结果。
4. 聚合结果的完整性验证仍主要保留在边缘侧，而不是转移给用户。
5. 允许异步的对象是“边缘窗口批次”，而不是单个用户上传。

因此，研究点2的优化目标可写为：

`min T_epsilon`

其中 `T_epsilon` 表示系统达到目标测试精度 `epsilon` 所需的实际训练时间或通信时钟长度。与此同时，需要满足：

- 用户更新隐私不被云端、边缘服务器或任一单个辅助服务器恢复；
- 云端无法在缺失任一辅助服务器部分掩码的情况下提前解掩码；
- 异步接收的陈旧批次不会无约束地主导全局模型更新；
- 掉线用户不会导致整个窗口的安全聚合过程失效。

## 3. 系统模型与符号定义

### 3.1 系统角色

- 用户 `u_i`：在本地数据上训练模型，并上传掩码后的模型参数。
- 边缘服务器 `e_k`：收集本组用户上传，完成窗口内预聚合与验证证据生成。
- 云服务器 `C`：接收已封窗的边缘批次，在获得双辅助服务器部分掩码后恢复明文批次，并异步更新全局模型。
- 辅助服务器 `A1`、`A2`：分别掌握独立种子材料，针对相同窗口生成各自的部分掩码。

### 3.2 聚合对象

当前实现聚合的是模型参数向量，而不是真正的单步梯度。因此，研究点2应继续采用参数平均语义，与现有 FedAvg 风格实现保持一致。也就是说，用户上传的是本地训练后的模型参数向量的掩码形式，云端恢复的是某个边缘窗口内的平均模型参数。

### 3.3 窗口定义

为兼容异步聚合与安全掩码生成，定义边缘窗口：

`omega = (e_k, s, v)`

其中：

- `e_k` 表示边缘服务器编号；
- `s` 表示该边缘上的窗口序号；
- `v` 表示该窗口基于的全局模型版本号。

每个窗口 `omega` 对应一个固定的参与用户集合 `S_omega`。只有当 `S_omega` 被边缘服务器封存后，两个辅助服务器才能基于该集合生成部分掩码。

### 3.4 掩码与聚合量

对于窗口 `omega` 中的用户 `u_i`，其本地训练后的模型参数记为：

`w_i^omega`

两个辅助服务器分别生成对应掩码：

`m_i^(1)(omega)`，`m_i^(2)(omega)`

用户上传的掩码参数为：

`wbar_i^omega = w_i^omega + m_i^(1)(omega) + m_i^(2)(omega)`

边缘服务器对窗口内用户求和得到：

`Wbar_omega = sum_{u_i in S_omega} wbar_i^omega`

两个辅助服务器分别计算窗口级部分掩码：

`M_omega^(1) = sum_{u_i in S_omega} m_i^(1)(omega)`

`M_omega^(2) = sum_{u_i in S_omega} m_i^(2)(omega)`

云端在收到两份部分掩码后恢复窗口明文聚合结果：

`W_omega = Wbar_omega - M_omega^(1) - M_omega^(2)`

再得到窗口平均模型：

`Wtilde_omega = W_omega / |S_omega|`

## 4. 协议流程

### 4.1 全局模型下发与窗口开启

云端维护当前全局模型 `W^(v)` 及其版本号 `v`。边缘服务器在收到当前全局版本后，为其负责的用户开启一个活动窗口 `omega = (e_k, s, v)`。该窗口在创建后接收一段时间内到达的用户上传，但所有加入该窗口的用户都必须基于相同的全局版本 `v` 开展本地训练。

### 4.2 用户本地训练与窗口化掩码上传

用户从所属边缘服务器获得窗口标识 `omega` 和当前全局模型 `W^(v)`，在本地数据上完成训练后，生成掩码模型参数 `wbar_i^omega`，并上传到对应边缘服务器。这里的关键变化是：掩码不再单纯绑定到全局轮次 `t`，而是绑定到窗口标识 `omega`。这样即便不同边缘服务器的提交时刻不同，只要窗口标识不同，掩码空间就天然隔离，不会发生跨批次串扰。

### 4.3 边缘服务器封窗与本地预聚合

边缘服务器对窗口 `omega` 内已到达的用户上传进行缓存。当满足以下任一条件时，窗口被封存：

1. 到达用户数达到最小聚合阈值；
2. 等待时间达到预设超时；
3. 风险控制规则判定该窗口应立即提交。

窗口一旦封存，其参与集合 `S_omega` 不再变化。随后边缘服务器计算：

- 窗口掩码参数和 `Wbar_omega`；
- 对 `Wbar_omega` 的线性同态哈希；
- 相应签名或其他验证证据。

边缘服务器将 `omega`、`S_omega` 的摘要信息及 `Wbar_omega` 提交给云端，并把同一窗口的参与集合发送给两个辅助服务器。

### 4.4 双辅助服务器部分解掩码

辅助服务器 `A1` 和 `A2` 收到相同的窗口标识 `omega` 与用户集合 `S_omega` 后，分别独立计算本窗口的部分掩码 `M_omega^(1)` 和 `M_omega^(2)`，并生成对应的掩码哈希或辅助验证材料。云端只有在同时获得两份部分掩码之后，才能对该窗口完成解掩码。

### 4.5 云端异步融合

与同步方案不同，云端不再等待所有边缘窗口到齐后统一更新，而是对每个“已完整到达”的窗口独立处理。对于任意已完成的窗口 `omega`，云端恢复其平均模型 `Wtilde_omega` 后，计算其相对于当前全局版本的陈旧度：

`s_omega = v_current - v`

其中 `v` 为窗口创建时使用的基模型版本，`v_current` 为窗口提交到云端时系统当前的全局版本。然后为该窗口分配一个陈旧度感知的融合权重 `lambda_omega`，例如：

`lambda_omega = lambda_0 / (1 + s_omega)`

据此更新全局模型：

`W^(v_current + 1) = (1 - lambda_omega) W^(v_current) + lambda_omega Wtilde_omega`

该更新方式本质上是“窗口平均模型与当前全局模型的加权融合”，与当前仓库中基于参数向量的异步实现保持一致。

### 4.6 边缘验证

为保持研究点1的可验证性设计，边缘侧继续承担主要验证责任。对于每个窗口，边缘侧验证应满足如下关系：

`H_plain(omega) + H_mask^(1)(omega) + H_mask^(2)(omega) = H_masked(omega)`

其含义是：窗口明文聚合结果的哈希与双辅助服务器部分掩码哈希相结合后，应能还原窗口掩码聚合结果的哈希。由此可防止云端在异步处理过程中伪造窗口聚合结果。

## 5. 为什么只能做“组间异步”，不能直接做“全异步”

这个点在答辩或和导师讨论时非常重要，可以直接这么解释：

1. 研究点1的安全聚合依赖一个已经固定的参与集合；没有固定集合，就无法正确生成窗口级全局掩码。
2. 两个辅助服务器必须对同一批用户集合计算部分掩码；如果客户端逐个异步到达并随到随算，就无法保证两个服务器看到的是同一集合。
3. 边缘验证依赖于“一个窗口内的掩码和、明文和、部分掩码哈希”之间的对应关系；如果没有封窗，这种对应关系就会被破坏。
4. 因此，与现有密码结构兼容的不是客户端级全异步，而是“窗口内相对同步，窗口间异步提交”的半异步架构。

换句话说，半异步不是退而求其次，而是由密码协议约束出来的合理选择。

## 6. 与 FedFleet 的关系与区别

FedFleet 的核心启发是“组内同步、组间异步”。这一点与本研究非常契合，因为它天然适合处理设备异构带来的拖尾问题。

但是，FedFleet 只解决训练调度与陈旧更新权重问题，并不处理以下安全问题：

- 如何对边缘批次中的用户参数进行隐私保护；
- 如何在异步条件下恢复批次明文而不暴露单个用户参数；
- 如何验证云端没有篡改批次聚合结果；
- 如何保证两个辅助服务器始终基于同一批参与者工作。

因此，本研究不是简单照搬 FedFleet，而是在其“组内同步、组间异步”的训练组织思想上，叠加研究点1中的双辅助服务器安全聚合与边缘可验证机制，形成一种面向分层安全联邦学习的半异步扩展方案。

## 7. 可直接写进论文的“问题定义”版本

下面这段可以直接作为论文中的问题定义初稿：

“在研究点1提出的双辅助服务器可验证安全聚合框架中，系统采用严格的轮次同步机制完成边缘聚合、部分解掩码和全局更新。尽管该设计能够保证用户更新隐私和聚合结果完整性，但在设备异构、链路时延波动和用户掉线场景下，严格同步会显著放大拖尾节点带来的等待开销，限制系统的训练效率。为此，本章研究一个新的问题：如何在不破坏双辅助服务器部分掩码生成、边缘侧可验证机制以及掉线容忍能力的前提下，将现有同步分层联邦学习扩展为窗口化的半异步分层联邦学习机制。具体而言，本章以边缘窗口为异步基本单元，通过固定窗口参与集合、生成窗口级部分掩码、并在云端执行陈旧度感知的异步融合，实现兼顾隐私保护、结果可验证性与训练时延降低的分层联邦学习方法。” 

## 8. 可直接写进论文的“主要创新点”版本

1. 在双辅助服务器可验证安全聚合框架基础上，提出一种窗口化半异步分层联邦学习机制，使异步更新能够与固定参与集合下的安全聚合流程兼容。
2. 设计面向边缘窗口的部分解掩码机制，将掩码生成、窗口标识和参与集合绑定，保证异步条件下双辅助服务器仍能独立、一致地完成部分掩码计算。
3. 提出陈旧度感知的窗口级异步融合策略，在降低同步等待开销的同时抑制陈旧批次对全局模型稳定性的影响。
4. 保留边缘侧验证路径，使云端即使在异步更新场景下也无法伪造或篡改聚合结果，从而实现隐私保护、完整性验证与时延优化的统一。

## 9. 实验设计建议

研究点2的实验不要一开始搞太复杂，建议先做最稳的一版。

### 9.1 对比对象

- 同步 HVSA：研究点1的原始同步方案。
- 半异步 HVSA：窗口化、组间异步的扩展方案。
- 若后续需要，再增加 FedFleet 式调度基线或普通异步 FL 基线。

### 9.2 关键指标

- 达到目标精度所需时间；
- 相同训练时长下的测试精度；
- 平均窗口等待时间；
- 窗口平均陈旧度；
- 聚合通过率与验证失败率；
- 通信与密码开销增量。

### 9.3 参数敏感性

- 最小窗口大小；
- 窗口超时时间；
- 异步融合权重 `lambda_0`；
- 最大可接受陈旧度；
- 用户掉线率与 Non-IID 强度。

## 10. 一句话总结

研究点2最合适的定义不是“做一个全异步 FL”，而是“在研究点1的双辅助服务器可验证安全聚合框架上，设计一个与密码流程兼容的窗口化分层半异步聚合机制”。这个表述稳、真实，也更容易做出完整成果。
